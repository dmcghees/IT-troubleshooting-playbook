# Support Ticket Documentation

## Purpose

Clear ticket documentation helps technical teams understand what happened, what has already been tested, and what still needs attention.

Good documentation should be concise, specific, and useful to the next person who reviews the issue.

## Information to Include

A useful support ticket should normally include:

* User or department affected
* Device or system involved
* Description of the issue
* Exact error message when available
* When the issue started
* Troubleshooting steps completed
* Results of each step
* Current status
* Next action or escalation point

## Example: Weak Ticket Note

**Issue:** User cannot log in.

**Notes:** Tried a few things. Still not working.

This does not provide enough information for another technician to continue efficiently.

## Example: Strong Ticket Note

**Issue:** User unable to access company application after password reset.

**Symptoms:** User receives an "Access Denied" message after entering valid credentials.

**Troubleshooting completed:**

* Confirmed correct username
* Verified new password was being used
* Confirmed multi factor authentication was successful
* Tested another company system successfully
* Restarted the application and attempted login again

**Result:** User can access other company services, but the affected application continues to return an access denied message.

**Next step:** Escalated to the application administrator for permission review.

## Writing Effective Notes

Ticket notes should focus on facts rather than assumptions.

Instead of writing:

"Network is broken."

Write:

"User is connected to the workplace WiFi but cannot access websites. Two nearby users are experiencing the same issue."

The second version gives the support team useful information without assuming the cause.

## Document Changes Clearly

If a setting is changed, document:

* What was changed
* Why it was changed
* Whether the change resolved the issue
* Whether the original setting was restored

This creates a clearer troubleshooting history.

## Protect Sensitive Information

Do not place passwords or sensitive authentication information in support tickets.

Follow company policies when documenting personal, confidential, or security related information.

## Escalation Notes

When escalating a ticket, include enough information so the next support person does not need to repeat basic troubleshooting.

A strong escalation should summarize:

* The original problem
* Who or what is affected
* Troubleshooting already completed
* Current symptoms
* Any relevant error messages
* What type of additional support may be needed

## Example Escalation Summary

**Issue:** Shared office printer unavailable to multiple users.

**Scope:** Three employees on the same floor are unable to print.

**Troubleshooting completed:** Confirmed users are connected to the network, checked printer power and display, restarted the printer, and tested from multiple computers.

**Result:** Printer remains offline for all tested users.

**Next step:** Escalated for network printer configuration review.

## Key Takeaway

Good ticket documentation saves time, improves communication, and makes technical support more consistent.
